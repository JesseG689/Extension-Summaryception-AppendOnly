# Engine

## Memory model

- Layer 0 summarizes turns selected beyond dynamic verbatim window. `[STATE]` is a complete bounded rolling snapshot, not a delta; new snippets carry `stateMode: snapshot-v1`, and injection uses only the newest snapshot.
- `layer0-compression.js` validates Layer 0 sections independently after cleanup and integrity validation. `layer0SummaryTokenTarget` is the `[NARRATIVE]` anchor T (clamped [80,500]): validation accepts 0.4xT–1.5xT plus a narrow 1.65xT repair ceiling, avoiding retries on provider near misses. Rolling `[STATE]` is modular: to support user-enabled category toggles it uses a 500-token soft target, 600-token model-facing maximum, and a 2,640-char deterministic-compaction target (kept below the 3,000-char injection safeguard so accepted trims land safely under the token hard max even for denser scripts); the deterministic-repair ceiling is 1,000 tokens. Each category is also bounded by its own `STATE_CATEGORY_CHAR_BUDGET` in `summarizer-state.js` — `compactSnapshotState` runs the per-category trim even when the global budget is under-run, with `current_date_time` exempt (priorityRank -1 = carried verbatim). Provider output caps are separate; never derive them from `layer0SummaryTokenTarget`.
- Layer 0 `[STATE]` size compaction: `prompts.js` runs deterministic snapshot compaction (`compactStateNearMiss` → `summarizer-state.js` `compactStateSnapshotText`) **without a magnitude gate** — any oversized state is trimmed once on the first validation pass, and a post-trim token check rejects what still can't fit. There is no second salvage pass: the compactor is deterministic, so retrying it yields an identical result. Do NOT reintroduce an upper-token/char ceiling that refuses to try compaction (the old 360-token gate did this): dense (Cyrillic) blocks measured over the ceiling but trim cleanly, and refusing them forced wasteful full LLM retries on the very outputs the compactor was built to handle. The token-count fallback estimator in `token-count.js` (`APPROX_TEXT_UNITS_PER_TOKEN = 4`) is the single change-point if the chars-per-token ratio ever moves; the compaction char budget (`STATE_SNAPSHOT_COMPACTION_TARGET_CHARS = 2640`) is sized to match it, plus the per-category `STATE_CATEGORY_CHAR_BUDGET` caps the longest single category from monopolizing the global budget.
- `src/core/token-budget/` builds the `<summaryception_source_budget>` prompt block. `structural-constraints.js` is the single source of truth for sizing: per-layer acceptance bands (`LAYER_MIN_RATIO`/`LAYER_HARD_MAX_RATIO`, multiples of the slider target T), the 1.65x L0 repair ratio, per-layer safety multipliers, the `STATE_KEY_CEILING` (12) line ceiling, and `computeSentenceCap(layer, T)`, which converts a backend bound into a countable sentence cap. `budget-hint-builder.js` renders only those caps — prompts never contain token figures or percentages, because the model cannot count tokens while streaming. It also exports the shared `buildSizeTargetLine` and `buildSizeConstraintsBlock` helpers, which format the `at most N sentences/lines` size line and the wrapper block used by both the L0 budget hint and the L1+ `summaryception_promotion_constraints` tail block — one phrasing source per surface, so a retune touches a single place. `repair-feedback-adapter.js` appends sentence/line-delta repair feedback (`computeSentenceCap` for narrative, STATE lines `computeStateLineCap` = `min(keys||12, 12)`); repair prompts speak in countable deltas, never token numbers. `buildLayer0BudgetHint` takes an optional `settings`; when supplied and no prior state exists, the state line cap is anchored to the enabled modular categories via `getActiveLineCap(settings, STATE_KEY_CEILING)` instead of the raw ceiling — so enabling all six categories still reports `at most 12 lines` (the sum 36 clamps to 12), and the unclamped 36 never leaks. The hint is pre-computed in `summarizer-pipeline.js` `attachBudgetHint` (which now passes the effective `settings`).
- Snapshot state uses modular continuity fields (the enabled subset of `STATE_CATEGORIES`), a 600-token generated-output ceiling, and a 3,000-character injection safeguard. Legacy chats fall back to recognized fields from only the newest three Layer 0 snippets until their first snapshot is written. All six `stateCat*` flags default to enabled, so an old persisted settings object with no `stateCat*` keys backfills to all-categories-on through `getSettings()`; only a raw un-normalized object (as in unit tests) reads as `current_date_time`-only.
- Layers 1+ promote older snippets. Narrative is LLM-compressed by moderate macro priorities: durable transitions, names/places needed for continuity, lasting agreements, current position, and unresolved hooks survive; brands, errands, meals, clothing, one-off supplies, dialogue, and mechanical scene replay are dropped. Source-size compression accounting counts source narratives only; rolling states remain contextual input. Snapshot sources use the final snapshot in the promoted span, not merged or carried into a complete remaining snapshot.
- Promotion anchors bounds to the slider target T, not source size: L1 output must land in 0.4xT–1.75xT, L2+ in 0.3xT–1.5xT (`getPromotionSummaryTokenTarget`/`getPromotionSummaryTokenHardMax`). The soft target doubles as an over-merge floor — a too-short fold is rejected with reason `too-short` and gets one expand-the-fold repair. Promotion starts only for over-limit layers, and merges at least configured `snippetsPerPromotion` (defensively no fewer than three). `summarizer-promotion.js` owns quota details and reports when token pressure cannot progress because the minimum batch is unavailable.
- Any change to `store.layers`, snippet text/metadata, or related committed summary state must bump mutation epoch.

## Planning and execution

- `partition-planner.js` splits Layer 0 sources on assistant-turn boundaries using token-balanced partitions.
- `summarization-routes.js` normalizes Standard, Cache, Force, and Slop plans. Planner-specific countability stays inside planner modules.
- Cache auto-flush summarizes all planned partitions before one atomic commit, feeding each pending snapshot into the next partition's context. Force and Slop keep sequential partial commits.
- Shared route execution and promotion loops live in `summarizer-engine.js`; queue lifecycle in `summarizer-queue.js`.
- Prompt-affecting commits/effects queue while SillyTavern foreground generation is active. Generation end flushes pending work through `summarizer-commit.js`.
- Request-only prompt rewrites use `GENERATE_AFTER_DATA`, mutate final payload in place, and never persist rewritten roles/content into chat history. User-role masking applies to every outgoing `role: "user"` block, with marker-first, rewrite-all, marker-last, and keep-last-user modes; debug mode reports changed/kept counts in one collapsed console group with bounded content previews.

## Connections

- Adapters live in `src/core/connection-*.js`; `connectionutil.js` resolves routes and shared access.
- OpenAI-compatible SSE reads must reach `data: [DONE]`. EOF or disconnect before marker is retryable failure.
- Retry policy uses exponential backoff. Hard network failures such as `failed to fetch` or `ECONNREFUSED` skip normal primary retries and try configured fallback immediately.
- Per-attempt request timeout is configurable per route, stored in seconds on settings (`requestTimeoutSeconds` / `mergeRequestTimeoutSeconds` / `fallbackRequestTimeoutSeconds`) and resolved in `computeAttemptTimeoutMs` from `metadata.kind` + `metadata.useFallback`, not from the active connection. Retry attempts run at 75% of the first attempt's timeout so routes give up sooner to failover. Unset/invalid values fall back to hardcoded defaults (120s/90s layer0, 90s/60s promotion).
- Keep each connection source independently testable.

## Injection and ghosting

- `memory-injection.js` compiles one current-state block plus chronology. `memory-budget.js` applies injected-memory budget. The `injectCurrentState` setting (boolean, default true) gates whether `buildMemoryInjectionParts` prepends the `[CURRENT STATE]` block to the memory text bound for the RP prompt — direct injection, `{{summaryception_memory}}` macro, `/sc-preview`, and the inline preview all flow through `buildEffectiveMemoryText`, so they all follow the toggle; turning it off sends only `[CHRONOLOGY]`. The summarizer's own source-context paths (`buildFullContext`/`buildMemoryInjection` in `summarizer-batch.js` and `summarizer-promotion.js`) and the Layer 0 budget-hint path (`getCurrentStateSnapshotText`) bypass the flag, so the summarizer still sees prior state when generating summaries and the budget hint still reflects real state size.
- Effective injected memory uses compact `[start-end@YYYY-MM-DDTHH]` chronology anchors; summarizer and promotion context retain verbose anchors, and budget accounting follows the compact rendered form.
- Direct placement uses `setExtensionPrompt()`. Macro Only exposes `{{summaryception_memory}}` and clears direct injection.
- Ghosting uses SillyTavern `/hide`; originals stay visible in chat UI. Ownership tracked by `extra.sc_ghosted` and `store.ghostedIndices`.
- Clearing uses `/unhide` only for Summaryception-owned ranges. Reconciliation repairs missing ownership/visual hides and trims invalid indices.

## Prompt structure

- All six default summarizer templates (Layer 0 generate/repair, Layer 1+ promotion generate/repair) and both system prompts route through one assembler in `src/core/prompt-parts.js`: `buildSystemPrompt(role, invariants)` emits `<role>` + optional `<role_invariants>`; `buildUserPrompt({inputBlocks, schemaBlock, taskRules, criticalRules, triggerLine})` concatenates `<input>` blocks → `<output_schema>` → `<task_rules>` → `<critical_rules>` (omitted when empty) → a bare `EXECUTION_TRIGGER` imperative line as the final line. The tag order is the recency-bias defense — do not reorder or add anything after the trigger.
- **Durable rules live once, in the static templates — never in the runtime appenders.** `appendLayer0PromptConstraints` and `appendPromotionPromptConstraints` (`src/core/layer0-compression.js`) emit dynamic runtime content only: the pre-built `<summaryception_source_budget>` hint, `buildLayer0SourceRangeLine` output, and (promotion) the `[NARRATIVE]: merge into at most N sentences.` size line + `buildPromotionRepairLine` feedback. The size line is built by the shared `buildSizeTargetLine` helper (`budget-hint-builder.js`) so L0 and L1+ share one phrasing from one place. The `summaryception_l0_constraints` wrapper is gone; `summaryception_promotion_constraints` survives but holds only those dynamic lines. The promotion user prompt also carries an in-body `LENGTH CONTRACT (HARD LIMIT)` restating the sentence-cap rule; since prompts carry no token figures or percentages, a ratio retune needs no static-text rewording. Do not re-rest durable durability/date-format/language rules into the appenders — that re-creates the pre-refactor duplication and drift the assembler was added to kill.
- The runtime appenders do NOT append after the trigger. Each assembles its dynamic block then calls `insertBeforeTrigger(prompt, block, triggerLine)` (`src/core/prompt-parts.js`), which splits the assembled template at its trailing `EXECUTION_TRIGGER` line and re-inserts the block immediately above it — so `<summaryception_source_budget>`, the source-range line, `summaryception_promotion_constraints`, and `<summaryception_l0_repair_feedback>` (`appendRepairFeedback`, `request-runner.js`) all land before the bare imperative, leaving the trigger as the absolute final line. Custom user-edited templates that do not end with the expected trigger fall back to the old append-after behavior, so dynamic content is never lost.
- Tag names unchanged (owned by their emitters, asserted across test files): `<summaryception_source_budget>` (`budget-hint-builder.js`), `<summaryception_l0_repair_feedback>` and `summaryception_promotion_repair_feedback` (`repair-diagnostics.js` via `wrapperTag`). `<summaryception_memory>` is the unrelated `{{summaryception_memory}}` injection macro — do not touch it.
- Placeholder-token contract: `buildSummarizerPrompt`'s `.replace()` chain (`summarizer-pipeline.js`) is first-occurrence-only and substitutes `{{player_name}}`, `{{context_str}}`, `{{source_state}}`, `{{story_txt}}`, and `{{state_schema}}`. Each placeholder occurs exactly once per template; adding a second occurrence silently drops the second one's substitution. `{{state_schema}}` resolves at call time from the passed (effective) settings via `buildStateSchemaText` (`src/foundation/state-categories.js`); the schema text is the joined, `{cap}`-substituted fragments of the enabled categories in `priorityRank` order (always-on first) — token caps never appear, only the countable `{cap}` integers. `{{max_sentences}}` / `{{max_sentences_word}}` (digit + spelled cardinal for dual-framing the sentence cap inside `<output_schema>`) are filled separately by `appendPromotionPromptConstraints` (`layer0-compression.js`) from the same `computeSentenceCap` value that drives the tail `summaryception_promotion_constraints` size line — one source of truth, so the schema line and tail line always agree.

## Modular STATE catalog

- `STATE_CATEGORIES` in `src/foundation/state-categories.js` is the single source of truth for which `[STATE]` categories exist, their `sourceKey` settings flag, `priorityRank` (trim order, ascending; `current_date_time` rank -1 = never trimmed), `lineCapDefault`, help copy, and per-category schema fragment. Adding/removing/renaming a category fan-outs across: `defaultSettings` (`constants.js`) + `ExtensionSettings` (`types/globals.d.ts`), `KEY_ALIASES` + `SNAPSHOT_STATE_KEYS` + `STATE_CATEGORY_CHAR_BUDGET` (`summarizer-state.js`), `SCHEMA_FRAGMENTS` in the same module, the `{{state_schema}}` token in the L0 templates (`prompt-constants.js`), the budget-hint line cap (`budget-hint-builder.js`), and the settings.html toggle + `ui-events.js` binding + `settings-help.js` entry.
- A category checkbox needs **two** entry-layer wirings, not one: the `change` binding in `ui-events.js` `bindToggleHandlers()` (write path) **and** a `$('#sc_state_cat_*').prop('checked', s.stateCat*)` line in `ui.js` `updateUI()` (read-back path). With only the binding, the value persists but every panel re-render resets the box to the unchecked `settings.html` default — it looks exactly like "the setting doesn't save". The `date_time` input is `disabled`, so it is synced to a hardcoded `true`.
- The catalog is a pure foundation module — **it must not import from `core/`** (foundation → core violates the one-way layer flow). `getActiveLineCap(settings, ceiling)` therefore takes the ceiling as an optional param (default `Infinity` / unclamped) rather than importing `STATE_KEY_CEILING`; the core budget-hint builder passes the real ceiling. A future contributor tempted to `import { STATE_KEY_CEILING } from '../../core/...'` in this module: don't — thread the value through the call instead.
- `current_date_time` is `alwaysOn`: `isCategoryEnabled` returns true regardless of its persisted flag, so the disabled date-time checkbox in settings.html is informational only and the category always appears in `{{state_schema}}`.
- Chekhov bullet aging is schema-rule-driven (model-applied), not deterministic. Each summarizer call covers one batch of source turns (~15 in the f12 trace), so the schema fragment in `state-categories.js` instructs the model to age unlocked bullets by the **batch turn count**, not by +1 per call — the old "+1 per turn" wording produced inconsistent jumps (0→4→6→12 on one observed bullet). The rule also caps the per-call increment to the batch turn count and frees time-locked (`[LOCKED: T:HH:MM]`) bullets. If you touch the chekhov fragment, preserve the batch-aware aging wording or re-introduce the slip.
- **Easy-mode gotcha:** `buildEasyEffectiveSettings` (`src/foundation/state.js`) starts from `defaultSettings`, NOT from the user's saved settings. Any new category toggle that must take effect in Easy mode must be explicitly copied into that function's spread, or an Easy-mode user ticking the checkbox sees no change. All six `stateCat*` flags are copied there, each falling back to its own `defaultSettings` value.
- `inventory` is still in `COMPOSITE_MERGE_KEYS` (composite merge keeps a category's per-key history across snapshots). The removed legacy keys (`characters`/`dynamics`/`hooks`/`counters`) remain in that set as harmless dead membership — they no longer alias to a canonical key, so they can never match; their merge/prune branches (`pruneMergedStateValue`, `collectHookText`) are intentionally left in place rather than ripped out on a clean-cutover criterion (see the minimal-cutover decision on the modular-state work).

## Date-format contracts

### Prose dates (`[NARRATIVE]`)

- `[NARRATIVE]` prose dates must be calendar form only (`On July 6`): no year, no ISO syntax, no clock-time lead-in. The current year and exact hour are already carried by the `[STATE]`/scene-time `current_date_time` anchor and the JSON `currentDateTime` field — duplicating them into prose wastes tokens and causes per-entry opener drift (`On July 6, 2024,` / `On 2024-07-06,` / `On July 6 at 19:00` all appeared before the rule). A clock time may appear once mid-sentence only when it carries story weight (alarm, deadline, shift boundary).
- Enforced by one shared constant `PROSE_DATE_FORMAT_RULE` (`src/foundation/prompt-constants.js`), embedded once in each of the four default prompts' `<critical_rules>` block via the `prompt-parts.js` assembler (no longer appended by the runtime appenders). All four Layer 0 / Layer 1+ generate+repair sites must reference the same constant — do not inline a date-format spec in only one site (that is how the prior ISO-in-prose contradiction, e.g. the old `2024-07-12 Fri` example, leaked ISO dates into promotion prose).

### `[STATE]` `current_date_time` weekday auto-correction

- The model can hallucinate the `ddd` weekday token (observed in the f12 ERP trace: Call #14 emitted `2024-07-07 06 Wed` when Jul 7 2024 is Sun; an earlier prompt example `2024-12-03 06 Wed` was itself wrong — Dec 3 2024 is Tue — and the model imitated it). To make the weekday deterministic, `parseStateLines` (`src/core/summarizer-state.js`) re-derives it from the ISO date via `normalizeCurrentDateTime` on every parse.
- Correction happens at `parseSnippet`, the single convergence point for **every** snippet path (L0 batch commit, regeneration, promotion, memory injection, metadata extraction) — not at the individual write sites. So the stored `.text`, derived `currentDateTime` metadata (`snippet-metadata.js`), and the next call's `<prior_context>>` all see the corrected weekday; this breaks the carry-forward cycle that produced the original slip. Do not move it to `snippet-manager.js` or `summarizer-batch.js` — that re-fragments the boundary.
- Implementation contract: weekday is computed from `Date.UTC(year, month-1, day).getUTCDay()` **in UTC** (a local `new Date(y,m,d)` shifts the day in non-UTC tz). The round-trip check `getUTCFullYear/Month/Date === input` rejects impossible calendar dates like `2024-02-30`, and unparseable values (e.g. `someday soon`) fall through verbatim — the normalizer never fabricates. Stray minutes (`16:32`) are dropped in favor of the HH-resolution contract. Missing weekday tokens are inserted.
- Prompt defense in depth: the L0 generate and repair templates (`prompt-constants.js`) also instruct the model to derive `ddd` from the ISO date and never carry it across a date change. The normalizer is the deterministic backstop. When editing example dates in those prompts, verify the weekday against the ISO date (a wrong example propagates).
- Tested by `tests/summarizer-state.test.js` (covers the Call #14 regression, missing-weekday insertion, minute-dropping, impossible-date rejection, and verbatim fall-through).
