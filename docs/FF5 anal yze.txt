# Firm keep/move analysis — FF5 internal states → Summaryception memory

## How each block actually works (mechanics)

Decisive characteristics:
- **Persistence model** — Is the data rebuilt every turn or carried across turns? Per-turn output is not memory; carried state is.
- **Update locus** — Who updates it: the main RP model emitting the block, or our snapshot pipeline rewriting `[STATE]`?
- **Fire/decision rule** — Does the block decide the *current* turn's action via a fresh roll/formula (execution) or just store state?
- **Output contract** — Must the model emit this block *every* turn for the system to function?
- **Token math** — Captured, accumulating, dropped?

And one cross-cutting subtlety: FF5 leans on ST `{{setvar}}` constants (`bond_X_Y`, `gmNotebook`, `chekhovActive`). In the FF5 architecture those carry across turns *inside* the model's `internal_states` block — they're not native ST conversation memory. Moving to extension means our snapshot pipeline takes over that carrying job. We don't need `{{setvar}}` plumbing.

## Should the extension STATE cap grow?

Your today's cap: 7 keys, 200 token soft target, 300 hard max, 7 lines.

What lands in extension STATE after the move:
```
current_date_time, location, characters(+agendas+where merged), dynamics(+BOND pairs),
constraints, hooks + NEW: bonds, agendas(off-screen), bullets, gm_notes, titles, factions(optional)
```

That's not 7-into-7 anymore. Concretely, the *moved* content fits nothing if you keep the 7-line/300-token ceiling — the entire value of moving disappears and you're back to "garbo" by a different name.

Targeting the blocks listed and a 6–10-turn reasonable scale:
- `bonds` — up to ~6 pairs × `BOND x | Sparks y | Grudge z` = ~80 tokens
- `bullets` — up to ~8 active bullets × `[BULLET: ...] (weight, age/12)` = ~120 tokens
- `gm_notes` — up to ~12 entries × ~6 tokens = ~80 tokens (capped per your prune logic)
- `agendas` — ~3–5 NPCs × ~22 tokens = ~110 tokens
- `titles` — ~40 tokens
- existing keys: ~80 tokens

Total realistic cap needed ≈ **≈ 510–600 tokens.** But you only ever inject the *latest* L0 snapshot (L1+ carry no state), so the cap bites only on **model emission time** and **one injected block.** Even at 600 you stay well within L0 narrative tokens saved.

**Recommendation: raise cap to 500 tokens hard max, soft target 400.** That clears the counted content (~510) by shaving the least-durable sub-field, which is exactly what your `_repair` already does — drop the weakest lines. Going to 600 hard / 450 soft gives a one-line margin if you want to be conservative; bumping key-ceiling `STATE_KEY_CEILING` from 7 to ~12.
